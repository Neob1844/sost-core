[size=14pt][b][color=red]READ THIS BEFORE BUILDING A NEW NODE FROM SCRATCH[/color][/b][/size]

[b]A full synchronisation from the genesis block does not currently complete.[/b] This is a known, diagnosed defect and it is stated here because it decides whether the next section is useful to you.

A node starting from block 0 stops at [b]19 historical blocks between heights 4,160 and 5,410[/b], all produced in April 2026. The published binaries cannot re-validate them: consensus parameters were changed while those blocks were being mined, so the rules in force for them are not the rules the current code applies. Everything above height 5,410 replays exactly — 21,563 consecutive blocks and counting.

There is a second, separate defect in block serving: under load a node can leave a block frame half-written and keep sending, which desynchronises the receiving peer and makes it disconnect.

[b]Neither fix is deployed.[/b] A patch for the serving defect is written and tested in a branch; a bounded fix for the 19 blocks is designed but not implemented. Nothing here is claimed as fixed, and no external audit of this software has been performed.

[b]What this means in practice:[/b]

[list]
[li][b]If you already have a synced chain:[/b] nothing. Upgrade normally. Your node keeps working.[/li]
[li][b]If you are starting a node today:[/b] do not expect a sync from block 0 to finish. Start from a recent [tt]chain.json[/tt] instead, or wait until the fix ships.[/li]
[/list]

Your coins, your keys and your ability to mine are not affected by either defect. What is affected is a node's ability to serve the whole chain to a brand-new node.

[size=14pt][b]OPTION B — BUILD FROM SOURCE[/b][/size]

Compiling is optional; a downloaded binary whose SHA-256 matches is equally valid. If you prefer to build, these exact commands were run from a clean clone before this post and produced the [b]same published hashes[/b]:

[code]
# 1. build dependencies (Ubuntu / Debian)
sudo apt update
sudo apt install -y build-essential cmake git libssl-dev libsecp256k1-dev

# 2. get the tag
cd ~
git clone --depth 1 --branch v16.2.3 https://github.com/Neob1844/sost-core.git sost-v1623-src
cd sost-v1623-src
git describe --tags --exact-match          # must print: v16.2.3

# 3. configure and build — the build directory MUST be named "build"
cmake -S . -B build -DSOST_ENABLE_PHASE2_SBPOW=ON -DSOST_TESTNET_FORKS=OFF \
      -DCMAKE_BUILD_TYPE=Release
cmake --build build --target sost-node sost-miner sost-cli -j"$(nproc)"

# 4. verify against the published hashes
cd build
sha256sum -c <(grep -E '^[0-9a-f]{64}' ../docs/v16/SHA256SUMS)
[/code]

[b]Two things that decide whether your hashes match.[/b]

[list]
[li][b]The build directory must be called [tt]build[/tt].[/b] The source path is normalised out of the binary, so it does not matter where you clone; the build directory name is [b]not[/b] normalised. Building into [tt]build-v16[/tt] or [tt]out[/tt] produces different bytes from the same commit.[/li]
[li][b]A different toolchain legitimately produces a different hash.[/b] Cross-machine reproducibility is not claimed. Matching hashes are guaranteed only for the environment above (Ubuntu 22.04.5, gcc 11.4.0, glibc 2.35). A mismatch on a different compiler is expected and is not, by itself, evidence of tampering — but an [b]official downloaded[/b] binary must match exactly.[/li]
[/list]

If cmake stops with [tt]SbPoW requires libsecp256k1 with schnorrsig module enabled[/tt], your distribution's libsecp256k1 is too old: upgrade the package, or build libsecp256k1 with [tt]--enable-module-schnorrsig[/tt].

[size=14pt][b]BETWEEN #29,900 AND #30,000 — INSTALL AND RESTART[/b][/size]

[b]Stop the right process.[/b] Use your service name, or the exact PID. Never a blanket [tt]pkill -f sost[/tt]: on a machine that also runs a CLI or a second miner it kills things you did not mean to kill.

[b]A — node under systemd (typical on a server)[/b]

[code]
sudo systemctl stop sost-node
sudo install -m 0755 ~/sost-v1623/sost-node /path/to/your/build/sost-node
sudo install -m 0755 ~/sost-v1623/sost-cli  /path/to/your/build/sost-cli
sudo systemctl start sost-node
sleep 20 && systemctl status sost-node --no-pager | head -8
[/code]

Loading a large chain file takes a few minutes. That is normal; the miner will retry meanwhile.

[b]B — node or miner started by hand[/b]

[code]
pgrep -a sost-miner            # shows the PID and the full command line
PID=<the pid you just saw>     # check it IS your miner before continuing
kill "$PID"                    # by PID. Not by name, and not -9 first.
# wait for it to exit, then install:
install -m 0755 ~/sost-v1623/sost-miner /path/to/your/build/sost-miner
[/code]

[b]C — Windows / WSL[/b]

Same as B, inside your Ubuntu window. If the miner runs in its own terminal, press [b]Ctrl+C[/b] in that terminal — it stops exactly that miner and nothing else — then install the new binary and start it again with your usual command.

[b]Relaunch the miner — same flags you already use[/b]

[code]
cd /path/to/your/build
./sost-miner \
  --wallet ~/sost-keys/your-wallet.json \
  --mining-key-label "your-label" \
  --genesis genesis_block.json \
  --rpc 127.0.0.1:18232 \
  --rpc-user your-user --rpc-pass-file ~/.sost/rpc.pass \
  --blocks 999999 --max-nonce 500000 \
  --profile mainnet --realtime --threads 8
[/code]

[tt]--wallet[/tt] + [tt]--mining-key-label[/tt] select the key that [b]signs[/b] your blocks. Do not replace them with [tt]--address[/tt]: your V16 Jackpot eligibility and your NODE_BIND both depend on that signed identity.

[b]About [tt]--threads[/tt].[/b] It is a tuning knob, not a required value. ConvergenceX is memory-bandwidth bound, so more threads is not automatically faster and on many machines is slower. Start at [tt]8[/tt], try [tt]16[/tt], and keep whichever gives the higher [tt]stable/s[/tt] figure in your own miner log. The examples on sostcore.com use different numbers for exactly this reason.

[b]Node command line, for reference[/b]

[code]
./sost-node \
  --genesis genesis_block.json --chain chain.json \
  --rpc-user your-user --rpc-pass-file /etc/sost/rpc.pass \
  --profile mainnet --p2p-enc on
[/code]

[size=14pt][b]RPC PASSWORDS AND NODE SECURITY[/b][/size]

Every node operator uses their [b]own[/b] RPC credentials. There is no universal SOST RPC password, nobody can give you one, and nobody should ever ask you for yours. It is [b]not[/b] your wallet passphrase. The miner authenticates to [b]your[/b] node, so node and miner must use the same credentials.

[code]
mkdir -p ~/.sost && umask 077
openssl rand -base64 30 > ~/.sost/rpc.pass
chmod 600 ~/.sost/rpc.pass
[/code]

Then point everything at the file instead of typing the secret:

[code]
sost-node  --rpc-user your-user --rpc-pass-file ~/.sost/rpc.pass  ...
sost-miner --rpc-user your-user --rpc-pass-file ~/.sost/rpc.pass  ...
sost-cli   --rpc-user your-user --rpc-pass-file ~/.sost/rpc.pass  ...
[/code]

The file must be mode 600, owned by you, one line and nothing else — the binaries refuse anything else rather than reading a secret other local users can see. Anything typed on a command line is visible to every user on the machine through [tt]ps[/tt]; that is what this release removes.

If your node runs under systemd, name the [b]path[/b] in the unit, not the password:

[code]
ExecStart=/opt/sost/build/sost-node --genesis genesis_block.json --chain chain.json \
  --rpc-user ${RPC_USER} --rpc-pass-file /etc/sost/rpc.pass --profile mainnet --p2p-enc on
[/code]

[b]HTTP 401.[/b] From v16.2.x the miner prints [tt]*** RPC AUTHENTICATION REJECTED (HTTP 401) ***[/tt]. That is not a rejected block — the node never validated it. Check: same [tt]--rpc-user[/tt] on both sides; the password file holds one line and nothing else; the node was restarted after you changed its password; and you are talking to your own node.

Do not expose an unauthenticated RPC service to the public Internet.

[size=14pt][b]YOUR EXISTING WALLET AND SOST REMAIN COMPATIBLE[/b][/size]

You do not need to create a new wallet, change your mining address or transfer your SOST to upgrade. Existing v1 wallets remain supported, with no conversion and no deadline.

Encrypted v2 wallets are an [b]optional[/b] security improvement. Encrypting is NOT required to keep mining or to receive normal DTD rewards, and it does not change your address or your SbPoW identity. If you do it, the procedure never overwrites your only copy:

[code]
# 1. export an ENCRYPTED COPY (the original stays where it is)
sost-cli --wallet ~/sost-keys/your-wallet.json wallet-export \
  --encrypted --output ~/sost-keys/your-wallet.v2.json
#    the passphrase is typed twice, with the terminal NOT echoing it
#    for an unattended export, read it from a descriptor instead:
#      ... wallet-export --encrypted --output FILE --passphrase-fd 3 3< ~/.sost/wallet.pass

# 2. RECOVERY DRILL — restore into a different file and compare the ADDRESSES
sost-cli --wallet /tmp/restore-test.json newwallet
sost-cli --wallet /tmp/restore-test.json wallet-import \
  --encrypted --input ~/sost-keys/your-wallet.v2.json
diff <(sost-cli --wallet ~/sost-keys/your-wallet.json listaddresses | awk '{print $1}') \
     <(sost-cli --wallet /tmp/restore-test.json        listaddresses | awk '{print $1}') \
  && echo "SAME ADDRESSES"

# 3. only then mine one block with the encrypted wallet
sost-miner --wallet ~/sost-keys/your-wallet.v2.json --mining-key-label "your-label" \
  --wallet-passphrase-file ~/.sost/wallet.pass   ...rest of your usual flags...
[/code]

[b]Compare the addresses, not the whole line.[/b] [tt]listaddresses[/tt] also prints a balance, a UTXO count and a label; the restored copy carries an offline cache snapshot, so those columns can differ on a funded wallet while the keys are identical. The [tt]awk[/tt] above compares exactly what has to match.

[b]The passphrase flag is not the same in both tools.[/b] [tt]sost-cli[/tt] takes [tt]--passphrase-fd <n>[/tt]; [tt]sost-miner[/tt] takes [tt]--wallet-passphrase-file <path>[/tt] or [tt]--wallet-passphrase-fd <n>[/tt]. Both forms take a descriptor NUMBER or a mode-600 file path, never the passphrase itself.

[b]Keep the v1 file until the encrypted one has mined a block.[/b] The passphrase cannot be recovered: lose it and your backup and the SOST controlled by those keys is gone for good.

[b]Never share your private keys, wallet passwords or recovery information.[/b]

[size=14pt][b]DTD JACKPOT V2 — IMPORTANT INFORMATION[/b][/size]

The new consensus rules activate automatically at block #30,000.

[b]V16 changes who qualifies for normal DTD.[/b] This is the part most operators miss, so it is stated in full.

Normal DTD keeps everything you already rely on: the same payout logic, the same every-block cadence (3-of-3, as since V15 at #25,000), the same uniform selection and the same seed. It still needs [b]no[/b] NODE_BIND, [b]no[/b] heartbeats and [b]no[/b] PoPC bond. An active SbPoW miner keeps participating exactly as today.

What changes from #30,000 is [b]eligibility[/b]:

[list]
[li]The activity window drops to [b]288 blocks[/b] (~2 days). Mining one valid block inside that window is what qualifies you.[/li]
[li]The 6-block producer cooldown [b]yields[/b] if applying it would leave nobody eligible — the draw never stalls for lack of candidates.[/li]
[li]The 10%/288 anti-dominance gate is [b]armed only at 11 or more distinct miners[/b]. Below that it does nothing.[/li]
[/list]

A consequence worth saying plainly: while a single miner is active, that miner can take [b]100% of the block[/b] (50% miner + 50% DTD). That is the designed behaviour of a small network, not a bug.

[b]DTD Jackpot V2[/b] is a separate reward. To qualify for the first V2 Jackpot you need:

[list=1]
[li]a valid SbPoW mining identity;[/li]
[li]at least three valid mined blocks during the previous 2,016 blocks;[/li]
[li]a valid NODE_BIND linking that mining identity to your node.[/li]
[/list]

NODE_BIND becomes available after activation at #30,000. The first V2 draw is at [b]#30,186[/b], and its heartbeat requirement is [b]0/0[/b] — no epoch has completed yet, so nobody is excluded for lacking heartbeat history. It then ramps 1/1 -> 2/2 -> 3/3 and settles at the permanent 3-of-4 from #31,338. That ramp is one rule counting completed epochs, [b]not[/b] a second fork and not a second update.

[b]Creating your NODE_BIND (only after #30,000):[/b]

[code]
# the node key is NOT your wallet key and NOT your RPC password
mkdir -p ~/.sost && umask 077
openssl rand -hex 32 > ~/.sost/node.key
chmod 600 ~/.sost/node.key            # SAVE A COPY somewhere safe

# build the bind with the SAME label your miner signs blocks with
sost-cli --wallet ~/sost-keys/your-wallet.json \
  --mining-key-label "your-label" \
  createnodebind 1 --node-key-file ~/.sost/node.key
# -> prints the raw transaction hex; broadcast it:
sost-cli --rpc 127.0.0.1:18232 --rpc-user your-user \
  --rpc-pass-file ~/.sost/rpc.pass sendrawtransaction <the hex>

# let the node heartbeat by itself: add to its command line / unit
#   --node-key-file /etc/sost/node.key      then restart the node once

# check eligibility before #30,186
curl -s -u "your-user:$(cat ~/.sost/rpc.pass)" -H 'content-type: application/json' \
  --data '{"method":"checkhistoricaljackpoteligibility","params":["sost1your...address"],"id":1}' \
  http://127.0.0.1:18232/
[/code]

[tt]--mining-key-label[/tt] matters: the bind must authorise the key that actually signs your blocks. Omit it and the CLI uses the label [tt]default[/tt] — if your mining key carries another label the bind is useless. [b]This is why v16.2.3 exists:[/b] older CLIs had no such flag and always bound [tt]default[/tt]. The tool now names the mining key it bound and lists your wallet's labels when the one you asked for is missing.

The proof that your bind worked is not that the transaction was sent. It is [tt]checkhistoricaljackpoteligibility[/tt] answering [tt]"node_bound": true[/tt] and [tt]"eligible": true[/tt]. Check it before #30,186.

Node participation determines [b]eligibility[/b]. Valid Proof-of-Work determines Jackpot [b]weight[/b] — running more nodes adds none. The Jackpot spends the existing historical reserve: [b]no additional SOST is emitted.[/b] Being eligible is not winning.

[size=14pt][b]ROLLING BACK[/b][/size]

Nothing in v16.2.x changes the on-disk chain format, so a rollback is the old binary and nothing else — no reindex, no migration, in either direction.

[code]
sudo systemctl stop sost-node
sudo install -m 0755 /path/to/your/build/sost-node.prev.<timestamp> /path/to/your/build/sost-node
sudo systemctl start sost-node
[/code]

Every previous release stays downloadable with its own hash list. One caveat: a wallet you [b]encrypted[/b] with v16.2.x cannot be read by a pre-v16.2 binary — point the old binary at the v1 file you kept.
