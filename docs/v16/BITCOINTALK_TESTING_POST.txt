[size=12pt][b]HOW TO TEST FROM A CLEAN SYNC[/b][/size]

[b]Build.[/b] The SbPoW flag is mandatory: a binary built without it cannot produce blocks the network accepts after #7,100.

[code]
sudo apt update && sudo apt install -y build-essential cmake git libssl-dev libsecp256k1-dev

git clone --depth 1 --branch v16.2.3 https://github.com/Neob1844/sost-core.git sost-src
cd sost-src

cmake -S . -B build -DSOST_ENABLE_PHASE2_SBPOW=ON -DSOST_TESTNET_FORKS=OFF \
      -DCMAKE_BUILD_TYPE=Release
cmake --build build --target sost-node sost-miner sost-cli -j"$(nproc)"

# optional: verify you built the published bytes
cd build && sha256sum -c <(grep -E '^[0-9a-f]{64}' ../docs/v16/SHA256SUMS)
[/code]

The build directory must be named [tt]build[/tt] for the hashes to match; the source path does not matter. A different toolchain legitimately produces a different hash.

[b]Run the test suites.[/b]

[code]
cmake --build build -j"$(nproc)"          # builds every test binary
cd build && ctest --output-on-failure      # 119 test binaries
./test-casert                              # cASERT: 229 assertions
[/code]

Expected today: [tt]100% tests passed, 0 tests failed out of 119[/tt], and [tt]229 passed, 0 failed[/tt] for cASERT. (The older "193 passed" in previous versions of this post was the count before the V11–V16 work.)

[b]Clean sync.[/b]

[code]
cd build
cp ../genesis_block.json .
rm -f chain.json

# your own RPC password, in a private file — never on the command line
mkdir -p ~/.sost && umask 077
openssl rand -base64 30 > ~/.sost/rpc.pass && chmod 600 ~/.sost/rpc.pass

./sost-node --genesis genesis_block.json --chain chain.json \
  --connect seed.sostcore.com:19333 \
  --rpc-user myuser --rpc-pass-file ~/.sost/rpc.pass \
  --profile mainnet --p2p-enc on
[/code]

[b]Wait for the node to finish syncing before starting the miner.[/b]

[code]
./sost-cli --wallet wallet.json newwallet
./sost-cli --wallet wallet.json getnewaddress "test-miner"
chmod 600 wallet.json

./sost-miner \
  --wallet wallet.json --mining-key-label "test-miner" \
  --genesis genesis_block.json \
  --rpc 127.0.0.1:18232 --rpc-user myuser --rpc-pass-file ~/.sost/rpc.pass \
  --blocks 999999 --profile mainnet --realtime --threads 4
[/code]

[tt]--wallet[/tt] + [tt]--mining-key-label[/tt] select the key that signs your blocks (SbPoW, live since #7,100). Do not use [tt]--address[/tt] on its own: it is the pre-SbPoW path, and your V16 Jackpot eligibility and NODE_BIND both depend on the signed identity.

Explorer: [url=https://sostcore.com/sost-explorer.html]sostcore.com/sost-explorer.html[/url]

[size=12pt][b]REPORTING A PROBLEM[/b][/size]

Please include as much as possible:

[list]
[li]Operating system and version; RAM; native Linux / WSL2 / VPS[/li]
[li]Exact git tag or commit, and confirmation of a rebuild[/li]
[li]Whether the build used [tt]-DSOST_ENABLE_PHASE2_SBPOW=ON[/tt][/li]
[li]Whether you started from clean chain data[/li]
[li]Full node log; full miner log if mining started[/li]
[li]Whether the failure happened during sync, post-checkpoint validation, mining, or RPC use[/li]
[li]Approximate latency to the seed, if relevant[/li]
[/list]

Two things that look like bugs and usually are not:

[list]
[li][b]"timestamp too far in future" rejects interleaved with accepts.[/b] The miner stamps at least 60 s after the previous block while the node refuses anything more than 30 s ahead of its clock. The same block lands seconds later. Only [i]continuous[/i] rejects with no accepts are a fault — then suspect clock skew (check NTP; a laptop resuming from sleep can be minutes ahead).[/li]
[li][b]"RPC AUTHENTICATION REJECTED (HTTP 401)".[/b] Not a rejected block: the node never validated it. Node and miner must use the same credentials, and the RPC password is the one [i]your[/i] node was started with — there is no network-wide SOST RPC password.[/li]
[/list]

Report issues: [url=https://sostcore.com/sost-contact.html]contact page[/url] or this thread.

[size=12pt][b]HISTORICAL RECORD — THE 4,100–5,750 CALIBRATION ERA[/b][/size]

[i]Kept because it is the record of what external testers found and what was fixed. It describes the network as it was around block 5,750, not as it is now.[/i]

[b]What was found[/b]

[list]
[li]Historical blocks served without sufficient proof data for full CX verification[/li]
[li]Checkpoint gaps: new peers reached the assumevalid boundary and failed on the immediate post-checkpoint blocks[/li]
[li]Sync-mode peers incorrectly penalised by the P2P rate limiter[/li]
[li]High-latency / packet-loss conditions exposing incomplete block transport[/li]
[li]cASERT equalizer profile oscillation (H3↔H12) from a slew-rate recomputation bug[/li]
[li]Anti-stall threshold scaling to 11 h+ at high lag[/li]
[li]Blocks accepted without [tt]profile_index[/tt], causing E1-style validation instead of H12[/li]
[li]bitsQ dropping aggressively during equalizer braking, undoing part of the correction[/li]
[li]Miner not detecting anti-stall profile changes, grinding at 0% stability[/li]
[li]RPC connection accumulation ([tt]CLOSE-WAIT[/tt]) eventually crashing the node[/li]
[li]V3.1 fallback-without-label: [tt]BlockMeta::profile_index[/tt] defaulted to 0, making legitimate B0 blocks indistinguishable from missing values and silently disabling the ±3 slew rate[/li]
[li]Deterministic B0→H6→H9→H12→stall oscillation every ~30 blocks, caused by a static-state variable inside the Ahead Guard path[/li]
[li]Stale [tt]test_checkpoints.cpp[/tt] referencing removed constants, breaking fresh-clone builds (reported by colerus)[/li]
[li]H10 stability cliff: scale jumped from 2 (H9) to 3 (H10), making H10+ unreachable (vostokzyf, oswaldzc)[/li]
[li]Slew rate ±3 producing a B0→H3→H6→H9→stall sawtooth[/li]
[li]H11 non-viable on modest hardware: 0.0% stability over 60–70+ minute stalls[/li]
[li]Two-controller coordination problem: bitsQ and equalizer correcting simultaneously, H9↔H10 oscillation with lag accumulating past 19 blocks[/li]
[li]Anchor-based exponential bitsQ accumulating lag since genesis — a 27% difficulty spike at block 5,150[/li]
[li]Fixed 12.5% cap too aggressive for the avg288 controller: bitsQ rose 12.7 → 16.1 bits in 50 blocks[/li]
[li]avg288 dead-band trap: 5-second blocks and 67-minute blocks cancelling in the arithmetic mean, leaving bitsQ stuck for 17+ consecutive blocks[/li]
[li]Relief valve at H1 insufficient: H1 blocks still taking 10–40 minutes because most miners lacked lag-adjust and missed the profile change[/li]
[li]Profile floor enforcement gap at block 5,525: miner declared H1 when context required H9/H10[/li]
[li]Slew descent stuck during stalls: the profile could not descend more than one level per block even after 53+ minutes with no block[/li]
[/list]

[b]What was fixed[/b]

Dynamic assumevalid/checkpoint updates · sync-mode exemption from misbehaviour scoring · relaxed sync traffic limits · fast-sync for trusted historical ranges · P2P transport hardening for high-latency links · the V3 → V3.1 → V4 → V5 → V6 cASERT sequence listed in the timeline above · direct lag mapping and asymmetric descent · profile floor enforcement · relief valve and margin recalibration · miner lag-adjust reduced from 30 s to ~6 s · avg288 controller with dynamic cap and median288 override · multi-threaded mining ([tt]--threads N[/tt]) · real-time hashrate display · the RPC [tt]CLOSE-WAIT[/tt] fix (socket timeouts, shutdown, linger) · fake-height peer detection and disconnect.

[b]Since then[/b], the work moved on to SbPoW and the DTD lottery (V11 Phase 2), capsules and Slingshot (V12), the E7–H35 ceiling and Beacon (V13), HTLC (V14.5/V14.7), the emission transition (V15) and now Jackpot V2 (V16). The V16.2.x releases also removed operator secrets from process command lines and replaced the CLI's hand-rolled JSON parsing in every path that handles funds.
