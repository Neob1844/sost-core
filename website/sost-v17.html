SOST V17 — Network Upgrade at Block #40,000

SOST is preparing a coordinated network upgrade targeting block #40,000. Proposed improvements include revised mining and DTD rewards, new coinbase maturity rules, stronger reorganization safeguards, improved P2P synchronization and enhanced node and wallet security. Node operators and miners must prepare compatible, verified software before activation. The release remains subject to final testing and approval.

EconomicsRewards: 80 / 10 / 5 / 5 (proposed)

Before #40,000 this is a proposal, not an active rule. Every block below #40,000 keeps the current rule: 50% to the miner and 50% to the DTD, fees included.

Proposed revision (17 November 2026): reserve 5% of every block subsidy for a Useful Compute vault, taken from the DTD share (15% → 10%). The V17 candidate code (include/sost/v17_economics.h, spec docs/v40000/V17_ECONOMICS_NORMATIVE.md) still implements 80 / 15 / 5; the new split needs code changes, tests and review before it can be part of a published release.   • Per block, in integer units (1 SOST = 100,000,000 stocks): DTD = subsidy × 10 / 100, J = subsidy × 5 / 100 and U = subsidy × 5 / 100, each rounded down; the miner receives the rest. The miner therefore absorbs any rounding remainder (at most 3 stocks), and the four parts always add up to the subsidy exactly.
  • Fees: 100% to the miner of the block. They are not split, not burned.
  • DTD: paid every block to one eligible winner, as today. If nobody is eligible, the 10% rolls over to the next block, as today.
  • Useful Compute vault U (proposed): a consensus balance (no address, no key, no custodian) that would grow by 5% of each block subsidy, about 0.39 SOST per block today. It would pay rewards only for computation verified independently, never twice for the same task. The verification and payout rules are still being designed; until they are specified, tested and activated, U cannot be spent.
  • Accumulator J: a consensus balance (no address, no key, no custodian) that grows by 5% of each block subsidy, about 0.39 SOST per block today (about 113 SOST per 288-block Jackpot cycle).
  • Jackpot prizes: unchanged rules — every 288 blocks, base 100 SOST, rollover up to a 500 SOST cap, Jackpot V2 winner (NODE_BIND + heartbeats, weighted by PoW). Only the funding changes: the historical reserve H pays first; when H is not enough, J pays the rest. The first V17 Jackpot is at #40,266.
  • Historical reserve: H (about 64,674 SOST today) stays reserved for Jackpot payments only. It is not moved and not reassigned.
  • Supply: the emission schedule and the maximum supply (~4.669 M SOST) do not change. No new SOST is created and nothing is burned: J and U only hold back part of the subsidy and pay it out later. At every height: unspent outputs + pending DTD + J + U = everything emitted.
  • Maturity of payouts: the miner output and J-funded Jackpot payouts follow coinbase maturity; H-funded payouts stay immediately spendable, as today.

SpendabilityCoinbase maturity: 1,000 and 5,000 blocks

Decision pending. The participation-based maturity has two variants (B and C) that are incompatible with each other. Both were tested on a devnet (20/20 each); the choice is the owner's and has not been made. If no decision is taken in time, V17 ships without this rule and maturity stays at 1,000 blocks for every coinbase output. This page will not present either variant as final before that decision.

The rule in force today (and in V17 unless a variant is approved)

Every coinbase output can be spent after 1,000 confirmations. A reward with fewer confirmations is immature and is not spendable: wallets and the Explorer must show it as immature, never as available.

  • Not retroactive: rewards created before #40,000 keep the 1,000-block rule.
  • Fixed at creation: the maturity is decided when the reward is created; gaining or losing eligibility later does not change it.

  • Where to see it: on the maturity development branch the CLI and the local wallet already read the per-output maturity (tested 10/10). The web wallet, the Digital Vault and the Explorer still have to display it before the rule can be activated.

SecurityReorganization and network safety

V17 does not change how the best chain is chosen: it is still the valid chain with the most accumulated work, with the existing 500-block reorganization cap. A new work rule was studied in depth and rejected for #40,000 because simulations did not show it to be safe enough. What V17 adds is hardening of the node around that rule. Results below are from the lab gates on the integrated candidate (13 November 2026, private test networks, not mainnet):

  • Chain file writes: the chain file is no longer rewritten on every block. This removed the main sync bottleneck (measured on 21,869 real blocks: complete in 300 s instead of 6,487 blocks in 8 minutes) and the window in which a crash could damage it.
  • Checkpoints: unchanged.
  • Malicious peers: fake “done” messages, stale replies and resubmitted forks are handled without penalising honest slow peers.
  • Immature funds: immature outputs stay unspendable through reorganizations.
  • Still pending before release: a full sync of the real mainnet history with the final V17 binary, and the merge of the pinned cryptographic library (below).

No software can make reorganizations impossible, and nothing protects against an attacker with a majority of the hashrate. With mining concentrated in two addresses today (see Decentralization), confirmations should be counted conservatively.

Wallet securityDigital Vault and web wallet

These protections are built and tested in the lab (end-to-end on a devnet: 45/45 checks). They are not yet in the production wallet. They are not consensus rules and do not depend on block #40,000.

ProtectionStatus
Tiered authorization of every send: 100 / 500 / 1,000 SOST levels, password or security key above the first level, cumulative limits per period, cancellable delay for large sendsTESTING
Check of the exact bytes about to be broadcast (recipients, amounts, fee, change), with alerts for address substitution and unusual feesTESTING
No two operations at once from two tabs or windows (the race found in the audit is fixed)TESTING
Authorizations expire (2 minutes) and cannot be reusedTESTING
Immature outputs never counted as spendableTESTING
Safe recovery and backup files, protection against key lossTESTING

Important limit: these checks run in the browser. While a wallet is unlocked its key is in the page’s memory, so malicious code in the page or a malicious extension could sign without them. They protect against mistakes and many attacks, but they are not an independent cryptographic control such as a separate signing device or multisig.

EthereumSOST ↔ wSOST Atomic Bridge — under development

UNDER DEVELOPMENT The bridge is not part of V17 and is not activated by it. It needs its own security review and its own launch authorization. No bridge contract holds real funds.

  • Design: 1:1 in both directions. Native SOST is locked on the SOST chain; the same amount of wSOST is delivered on Ethereum; returning wSOST burns it and releases the SOST.
  • Reserve: verifiable on-chain at any time (locked SOST = wSOST in circulation).
  • Verification: a light client of the SOST chain on Ethereum checks the PoW of the relevant blocks; independent watchers can raise alarms. Measures against double spending and a confirmation depth against reorganizations are part of the design.
  • Fees: no protocol fee. Users pay external Ethereum gas (lab measurement: about 190,000 gas per claim).
  • Ethereum L1 or L2: still being evaluated.
  • State: contracts and tests in the lab only. The native lock on the SOST side is not in the V17 consensus. Mining concentration must improve before a bridge can rely on SOST confirmations.
