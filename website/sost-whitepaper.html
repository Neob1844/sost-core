1. Summary

  • SOST is an independent Layer-1 proof-of-work blockchain. Mainnet has run since 15 March 2026 18:00 UTC, with no premine and no ICO.
  • Blocks target 600 seconds. Their proof of work is ConvergenceX, a memory-hard, sequential function about 8 GB in size.
  • Emission decays smoothly by a factor of e^−1/4 per epoch of 131,553 blocks, towards a maximum of 4,669,201.54789641 SOST.
  • Since block #25,000 every block pays 50 % to its miner and 50 % to the DTD (Decentralised Transaction Distribution), a draw among recent miners.
  • A proposed upgrade, V17, would change this to 80 % miner / 15 % DTD / 5 % Jackpot accumulator from block #40,000. It is not active and not released.

3. Consensus

3.1 Proof of work: ConvergenceX

  • Each attempt runs 100,000 sequential rounds over a 32×32 integer problem.
  • It uses a 4 GB dataset and a 4 GB scratchpad. Memory reads depend on the running state, and a program is generated per block.
  • A stability check closes the attempt. The result is a 32-byte commitment.
  • The reference miner is CPU-oriented; consensus does not enforce CPU-only mining.
  • Verification needs only a few megabytes.

3.2 Difficulty: cASERT

cASERT combines two independent controls:

  • bitsQ (Q16.16 fixed point, integer-only, per block) sets how rare a winning commitment must be.
  • The Equalizer selects one of 43 hardness profiles (E7 easing … B0 normal … H35 maximum). That profile sets the stability parameters every attempt must satisfy.

Every node recomputes both values and rejects a block that declares anything else.

3.3 Chain selection and finality

  • Nodes follow the valid chain with the most cumulative work.
  • Reorganisations deeper than 500 blocks are rejected.
  • On exactly equal cumulative work a node keeps the tip it saw first. V17 proposes TB-1: from #40,000, equal-work tips are ordered by a deterministic hash so every node picks the same one (section B). TB-1 only breaks ties; it never overrides more work and does not reduce what a majority of the hash power can do.
  • Coinbase outputs mature after 1,000 blocks. (V17 proposes 5,000 blocks for the miner reward of a miner that is not a DTD node participant; see section B.)
  • Hard-coded checkpoints in the source release fix the early history: 14 checkpoints, up to block #3,554.
  • Beyond those checkpoints, security is probabilistic proof of work. There is no validator quorum and no miner vote. A party with a majority of the hash power can produce a heavier chain (see §8).

3.4 Block identity

  • Since #7,100 every block carries a mandatory miner public key and a Schnorr (BIP-340) signature (SbPoW).
  • The DTD uses this as the miner's on-chain identity.

5. Block reward and the DTD

Heights Rule Status
0–24,999 normal blocks 50 % miner / 25 % Gold Funding Vault / 25 % PoPC Pool; from #7,100, draw blocks 50 % miner / 50 % DTD RETIRED
25,000 onwards every block: 50 % miner / 50 % DTD of subsidy + fees; 0 % to the vault and pool ACTIVE

Normal DTD (ACTIVE)

  • Each block draws one winner, uniformly, among addresses that produced a signed block in the last 288 blocks.
  • Cooldown rules apply. An unpaid share rolls over.
  • An anti-dominance rule excludes any address with ≥ 10 % of the last 288 blocks. Since #30,000 it is armed only when at least 11 distinct miners are in that window. Today the window holds 2, so the rule is not armed.

DTD Jackpot V2 (ACTIVE since #30,000)

  • Paid every 288 blocks since #25,290: base 100 SOST, cap 500 SOST, with rollover.
  • It is funded only by the frozen reserve (§6).
  • A winner needs ≥ 3 PoW blocks in the last 2,016, an active NODE_BIND and heartbeats in 3 of the last 4 epochs.
  • Weight is linear in PoW blocks, so running more nodes adds no weight.

Compatibility

  • Before #40,000 a V17 node validates exactly like V30000.
  • From #40,000, V16 nodes reject V17 blocks, so every node and miner must upgrade before that height.

Release criteria (all must be met):

  • gates pass on the exact release commit;
  • a replay of mainnet history reproduces the production UTXO-set root;
  • two independent nodes sync the full history;
  • fork-boundary tests pass;
  • the maturity decision is recorded (done on 15 November 2026: 1,000 / 5,000);
  • the build is reproducible;
  • operators are ready;
  • no P0 defect is open.

NO-GO procedure.

  • If a criterion fails, no release is published and V30000 keeps running. This creates no chain split.
  • The only alternative height prepared is #50,000, with a new build and full gates.
  • The height is never changed unilaterally.

Timing. At 600 s per block, #40,000 is about 4,754 blocks after #35,246, around 18 December 2026. The recent block rate is faster, so the date could be earlier. This is an estimate, not a commitment.

10. wSOST — PLANNED ETHEREUM ERC-20 INTEROPERABILITY

Status: PLANNED. NOT DEPLOYED. NOT AVAILABLE.

  • No wSOST contract exists on Ethereum mainnet or on any public test network, and no contract address has been published. Any address presented as "wSOST" is not from this project.
  • wSOST is not part of V17, and block #40,000 does not create, activate or list wSOST.

Intended design (implemented and tested only in a local laboratory):

  • wSOST would be an ERC-20 representation at 1 SOST = 1 wSOST.
  • A fixed inventory equal to the exact maximum SOST supply would be created once and held immobilised by the bridge contract. No mint and no burn would happen per operation.
  • A wSOST would leave the inventory only against a verified, keyless SOST deposit, and would return to it on exit.
  • There is no owner, administrator, upgrade path, manual pause or blacklist. The protocol fee is zero: users would pay only network gas.

Conditions before any deployment with value:

  1. new consensus rules on the SOST side (keyless deposit and release), which are not in V17;
  2. decentralised block production;
  3. an independent external audit;
  4. legal and regulatory review.

Retired designs: lock/mint with an off-chain authoriser, and a mandatory "Gold Access Key" paid in XAUT.

Not wSOST, not a reserve: an Ethereum account (0xd389…C7a6) that earlier versions of the website linked as network-held tokenized gold is an externally owned account, not a contract. It is not a SOST reserve and carries no commitment: SOST has no obligation to hold, add or maintain any gold, XAUT or PAXG, and holders have no claim on that account. It is not wSOST.

11. Universal Assets (native assets)

  • The native-asset layer (issuance, transfer and burn of user assets) exists in the code.
  • It is DEFERRED on mainnet: its activation height is INT64_MAX, so every asset operation is rejected (fail-closed). V17 does not change this.
  • The V17 candidate (RC6) includes the asset rules and a threshold-signature activation gate. Public issuance stays closed: reaching #40,000 does not open it, and no RPC, CLI, wallet or hand-built transaction can open it (36 tests on the mainnet build).
  • Gate governance (candidate, 15 November 2026): a one-time 2-of-3 bootstrap (three public keys compiled into the V17 rules; one key alone is not enough) can only install the first group of 2 to 5 custodians, with at least 2,016 blocks of notice, and has no power afterwards. This initial set is multi-signature protection, not decentralised governance by itself; custody is spread to independent custodians later by key rotation, without a fork. Custodians act with a quorum of at least 2-of-2, 2-of-3, 3-of-4 or 4-of-5 and can be replaced or re-sized later without a fork. A first opening or a key rotation needs 2,016 blocks of notice; lifting an emergency restriction needs 1,008. Any single custodian can veto a pending opening. The gate can only open or restrict the creation of new assets. It cannot move, freeze or confiscate SOST or existing assets.
  • Governance is pending. The three bootstrap public keys have not been provided. The official release build refuses to compile without them; a build without them keeps the mainnet gate closed, and it could then only be enabled by a later hard fork.
  • The website's "Asset Passport" registry is a web tool that records hashes off-chain. It does not issue on-chain assets.

12. Wallet and Digital Vault

  • The web wallet is self-custodial. Keys are generated and used in the browser, and the server never receives them.
  • Keys are encrypted locally with AES-256-GCM, using a key derived with PBKDF2 (100,000 iterations). The wallet auto-locks after inactivity.
  • Optional TOTP (two-factor) screens are interface protections only. They are not part of transaction authorisation and do not change what the key can sign.
  • Multisignature (sost3) addresses are not active on mainnet. Native multisig exists only in the V17 proposal.
  • The V17 candidate's Digital Vault (not published) adds: binding a mining address to a node (NODE_BIND, signed in two halves so the node key never enters the browser), heartbeat and DTD/Jackpot status, the maturity of each reward (1,000 or 5,000 blocks), manual coin selection, and a two-signature native multisig workflow that the wallet refuses before #40,000.
  • The wallet has not been externally audited.

13. Gold reference (unit of account)

  • SOST publishes an informational reference of 1 SOST ≡ 0.8886707657 mg of gold: one thousandth of the gold content of a 1944 Bretton Woods dollar.
  • The reference tracks the live gold price. It is not a market price, a peg, a floor, backing, a guarantee, a redemption or exchange right, or an economic commitment, and no reserve stands behind it. It is informational only and is not part of SOST tokenomics, which consist of Proof of Work + DTD and DTD Jackpot.
  • If SOST is ever traded, its price would be set by the market.

14. Security and risks

  • No independent external audit of the node, the wallet or any contract.
  • Concentrated block production (§8). A majority producer can reorganise up to 500 blocks and could censor transactions.
  • Small network. Few peers, one DNS seed, and the public infrastructure on one server.
  • Hard-fork coordination. Operators who do not upgrade before an adopted fork follow a different chain.
  • Retired contracts. The HTLC atomic swap contracts affected by finding H-01 are retired. Do not use them or send funds to them.
  • Experimental software. It may contain defects that cause loss of funds.
  • Regulatory uncertainty. No regulatory assessment, authorisation or legal opinion is claimed.
