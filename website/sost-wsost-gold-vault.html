Return — wSOST → native SOST

1 · CHECK
Any legitimate wSOST holder can use the return — including wSOST bought on an exchange. Enter the amount and your sost1… address.
2 · BURN
You burn N wSOST on Ethereum (you pay the gas). No XAUT is charged. The contract publishes the burn with a unique release id.
3 · RELEASE
After the burn is confirmed, the Bridge Vault releases N SOST to your address, minus only the published SOST network fee of that transaction. The release carries the release id, so anyone can match it.
HONEST LIMIT TODAY
SOST native multisig is not active, so the Bridge Vault could only be a single cold key and releases would be signed offline, not automatically. This is one of the reasons the bridge is not ready for production; secure native custody depends on the multisig planned for V17.

BRIDGE

What is wSOST?

RESEARCH NOT DEPLOYED

wSOST is not another coin. It is a token on Ethereum that represents native SOST one-for-one. The SOST it represents stays on the SOST blockchain, locked in a dedicated Bridge Vault, until the wSOST is turned back into SOST.

CANONICAL RULE
1 wSOST = 1 native SOST locked

Example — John wraps 500 SOST

JOHN HAS 1,000 SOST John wraps 500 SOST 500 SOST ──LOCK──▶ Bridge Vault (SOST chain) ══▶ 500 wSOST (Ethereum) RESULT 500 SOST remain native in John's wallet 500 SOST are locked in the Bridge Vault 500 wSOST exist on Ethereum NO NEW SOST WAS CREATED. The same 1,000 SOST still exist.

Example — John unwraps 200 wSOST

John burns 200 wSOST (Ethereum) 200 wSOST destroyed ══▶ 200 native SOST released from the Bridge Vault (minus the SOST network fee)
PERMANENT SOST INVARIANT
Only wSOST is burned during unwrap. Native SOST is never burned.

How a deposit would work (design)

sost-cli send <BRIDGE_VAULT> 500 --capsule-mode open-note \ --capsule-text "C701:0x<requestId>" # 71 of the 80 open-note bytes

The deposit carries a capsule (a data field active on SOST since block 7,350) with the id of your bridge request. That id is a public hash of the Ethereum recipient, the amount, the chain and the bridge contract, so your SOST signature binds the deposit to exactly that request. No consensus change, no new transaction type.

Why wSOST would exist

Integrating a brand-new Layer-1 is real work for wallets and exchanges; Ethereum and ERC-20 tokens are already integrated almost everywhere. wSOST would make SOST reachable from:

  • Ethereum wallets;
  • DEX liquidity pools and therefore public price discovery;
  • exchanges where ERC-20 support reduces Layer-1 integration work;
  • future DeFi compatibility.
WHAT IT DOES NOT DO
wSOST may reduce technical integration friction, but listing, liquidity, legal review and exchange due diligence remain independent requirements. It guarantees no listing anywhere.
ACCESS LAYER

Why wSOST — and why native SOST stays the real asset

RESEARCH NOT DEPLOYED

The integration barrier

One practical barrier to wider SOST market access is the technical burden a centralized exchange faces when it integrates a new, independent Layer-1 blockchain. Listing native SOST would require the exchange to:

  • run and maintain a SOST full node;
  • integrate SOST deposits and withdrawals;
  • implement a SOST-specific confirmation and reorganisation policy;
  • monitor wallet and node infrastructure around the clock;
  • review SOST RPC and transaction semantics;
  • build custody and operational tooling for a new chain;
  • carry the security and maintenance work specific to SOST.

Ethereum and ERC-20 infrastructure, on the other hand, is already in place at virtually every major centralized exchange: deposits, withdrawals, custody and monitoring for ERC-20 tokens are standard operations there. For such a venue, integrating an ERC-20 representation is operationally much simpler than integrating a new chain.

WHAT wSOST IS FOR
wSOST is intended to reduce integration friction for venues that already support Ethereum/ERC-20 infrastructure. It is being researched as an access layer. It does not guarantee that any exchange will list it, and listing, liquidity, legal review and exchange due diligence remain independent requirements.
native SOST → lock 1:1 → wSOST (ERC-20) → Ethereum wallets · DEX · compatible CEX infrastructure

What would be listed

The initial exchange-access target is wSOST: the representation offered to CEX and DEX venues where integrating the native SOST chain is impractical or unnecessarily complex. wSOST does not replace SOST. wSOST is designed to make SOST easier to integrate without replacing the native SOST network.

NATIVE SOST — THE CANONICAL ASSET
Native SOST remains:
  • the real Layer-1 asset;
  • the asset created and distributed by SOST consensus;
  • the asset received through mining, through normal DTD and through the DTD Jackpot;
  • the asset used for native transfers and in the SOST-side atomic swap;
  • the asset locked behind wSOST;
  • the final settlement asset when wSOST is unwrapped.
1 wSOST = 1 native SOST locked. Native SOST is the source asset; wSOST is only its external Ethereum representation. There is no independent wSOST monetary policy, no new native SOST is created by wrapping, and native SOST is never burned.

From the Genesis Gold Vault to Gold Reserve V2

The original SOST design introduced a Gold Vault concept from Genesis: part of the early block distribution accumulated in a constitutional reserve, with the long-term idea of connecting SOST with an external gold reserve. That historical architecture later changed. From block #25,000:

  • the Gold Vault receives 0% of new emission;
  • the PoPC Pool receives 0% of new emission;
  • the current block distribution is 50% miner / 50% DTD;
  • the historical Gold Vault + PoPC balances are frozen and committed to the DTD Jackpot.
THE HISTORICAL GOLD VAULT IS NOT REOPENED — ITS FUNDS ARE NOT REUSED
Gold Reserve V2 is a new and completely separate external reserve. Gold Reserve V2 is intended to continue the reserve philosophy introduced at Genesis, while preserving the historical Gold Vault exactly as committed under the current DTD Jackpot architecture. The old Gold Vault does not back wSOST, and Gold Reserve V2 does not reuse or alter its balances. HISTORICAL DTD JACKPOT RESERVE

How wSOST feeds Gold Reserve V2

wSOST and Gold Reserve V2 live on the same Ethereum infrastructure as tokenized gold such as XAUT. In the C701 design the reserve grows from one source only: the Gold Access Key each bridge user contributes in XAUT, paid straight from the user's wallet to the reserve inside the mint transaction.

N SOST locked → N wSOST issued (1:1, unchanged by the fee) small XAUT amount → Gold Reserve V2 (100% of the Gold Access Key) no new native SOST · no unbacked wSOST · no sale of wSOST from a treasury the historical Jackpot reserve is never touched

That gives the Genesis reserve philosophy a practical modern infrastructure — SOST L1 + the wSOST access layer + an external tokenized-gold reserve — while every accounting layer stays separate. DEVELOPMENT · NOT DEPLOYED

How the automated bridge would work

DEVELOPMENT NOT DEPLOYED

Nothing below can be done today. It describes the C701 target architecture (automated verification), prototyped and tested on a local development chain only. Design in development · not active · not ready for production.

1 · SOST → wSOST

1 You create a request: amount + your Ethereum address → request id (public hash) 2 Your SOST wallet sends the amount to the Bridge Vault, with the capsule C701:0x<request id> on that output 3 The verification engine would detect the deposit itself (no hash to paste) 4 It checks: right vault · exact amount · capsule = request · 30 confirmations (provisional) · output unspent · never used before 5 It signs ONE authorization bound to: chain id · bridge contract · recipient · amount · deposit txid:vout · expiry · nonce (+ a separately signed XAUT price) 6 In MetaMask you approve the XAUT Gold Access Key and send the mint transaction 7 In that single transaction the contract re-checks everything, moves the XAUT from your wallet to Gold Reserve V2 and mints exactly N wSOST to you 8 You get both proofs: the SOST deposit txid and the Ethereum transaction

A transaction hash typed by a user is only used to search or recover; it is never treated as proof. The engine always re-reads the SOST chain.

Price discovery — the 1:1 arbitrage

RESEARCH
Native SOST offered at $0.30 wSOST trading at $0.80 buy 1 SOST at $0.30 → wrap 1:1 → receive 1 wSOST → sell near $0.80 = +$0.50 Many people do it → SOST demand ↑ · wSOST supply ↑ → prices move together

So, once the bridge is liquid and freely usable, the wSOST market price is expected to become a market reference for native SOST. Prices are not guaranteed identical: bridge risk, fees, liquidity, access restrictions and finality delays can create temporary premiums or discounts. A large, persistent gap would mean wrapping is not freely available or the bridge is impaired.

TRUST MODEL

How the bridge would be secured — and what it cannot promise

NOT TRUSTLESS
Ethereum cannot read the SOST chain. The automated engine checks each deposit and signs the authorization, so the operator that holds the authorization keys is a central point of trust. In the current prototype, if those keys were compromised, wSOST without backing could be issued up to the caps until reconciliation pauses minting. For that reason the design is not ready for production.
BLOCKING SECURITY REQUIREMENT
A stolen verifier key must NOT allow minting wSOST without previously locked native SOST. Before production there must be a demonstrable property MINTED_WSOST <= VERIFIED_CONFIRMED_NATIVE_SOST_LOCKED, and the system must fail closed (no mint) whenever it cannot be demonstrated. The current prototype does not meet this yet.

The basic invariant is wSOST.totalSupply ≤ confirmed native SOST backing. That inequality is necessary but not sufficient: a deposit minted twice and a release paid twice can cancel out in the balance. WHAT THE VOTE IS NOT
SOST voting does not execute Ethereum state directly; guardians execute. If a sufficient guardian majority deliberately ignored a valid vote, the breach would be publicly provable from both chains, but SOST consensus cannot itself stop it. Security comes from four layers — guardians, SOST vote, timelock and the contract's destination restrictions. This is not trustless cross-chain governance.

// BEACON

Beacon — Advisory Channel

Signed operator notices, propagated between nodes. Advisory only. Does not affect mining rewards, block validity, chain selection, transaction validation, wallet balances, PoPC, Gold Vault, or consensus.

Phase II-A — local notices

Each node reads notices.json on startup. ECDSA-SHA256 signature verification against a hardcoded operator pubkey. Failure modes (bad signature, wrong network, expired, malformed) are silent drops. Active at V13_HEIGHT (12,000).

Phase II-B — threshold + revocation

Adds N-of-M threshold signatures (default 3-of-5), revocation by notice ID (only threshold-signed notices can revoke), and an optional mirror_url metadata field (never fetched by the node). Active at V13_HEIGHT.

Phase III — P2P gossip

Nodes gossip verified notices via a BCNN dispatcher with hard limits: 4 KB max notice, 32-notice LRU dedup cache, 8 notices/peer/min rate limit. Bad-signature notices are silently dropped; oversized/malformed/rate-limit hits earn peer misbehavior. Active at V13_HEIGHT.

Hard invariant. No Beacon code path links into block validation, mining validity, or chain commit. Beacon cannot reject, invalidate, or affect the canonical chain. Rollback is a single-line constant revert (BEACON_P2P_ACTIVATION_HEIGHT to INT64_MAX in include/sost/params.h).
