UPGRADE TO V16.2.3

For a node and a miner that are already running. The update window agreed with the network is after block #29,900 and before block #30,000.

You keep everything. Your SOST, your wallet file, your private keys, your SbPoW mining identity and your payout address are not touched by this upgrade. There is nothing to convert, nothing to move, no new wallet and no re-registration. Encrypting your wallet is optional and always will be.

The calendar

BEFORE #29,900 download v16.2.3, verify the SHA-256, back up. Do NOT switch yet. #29,900 → #30,000 THE WINDOW (~16–17 h): stop, install, restart. Node AND miner. AT #30,000 V16 consensus activates by itself. No command, no restart. #30,186 first DTD Jackpot V2 draw.

The window is a coordination convention, not a consensus rule: it exists so the whole network crosses the activation running the same build. v16.2.3 is consensus-identical to v16.1.0 — a node running either one follows the same chain. What is not optional is being off V15: a validating node still on old consensus software after #30,000 may diverge.

Already on v16.2.0 or v16.2.1? All v16.2.x releases ship the same sost-node and sost-miner, byte for byte, with the same published hashes. Only sost-cli changed. Replace the CLI and you are done — nothing needs restarting.

Step 1 — Before the window: get it and check it

Official binaries, no compiler needed:

mkdir -p ~/sost-v1622 && cd ~/sost-v1622 for f in sost-node sost-miner sost-cli SHA256SUMS; do curl -fsSL -O "https://github.com/Neob1844/sost-core/releases/download/v16.2.3/$f" done sha256sum -c SHA256SUMS chmod +x sost-node sost-miner sost-cli

It must print sost-node: OK, sost-miner: OK, sost-cli: OK. If any line says FAILED, stop and do not run the binary.

b253e4a9c352ea4b8557eec78d57e1c7619ab267af228c3e8f24bf8d7b69b897 sost-node 2ef9d0a77f243224ac088460818d6b360c689a7a3fa9555738e2b3b3e0112fe2 sost-miner 489f43741437a08b2d617c21020061c042f42d4609bbe6547d28f08ca5e07d07 sost-cli

Prefer to build it yourself? The build directory must be named build, or the hashes will not match — the source path is normalised out of the binary, the build directory name is not:

git fetch --all --tags --prune git worktree add ../sost-v1622 v16.2.3 && cd ../sost-v1622 cmake -S . -B build -DSOST_ENABLE_PHASE2_SBPOW=ON -DSOST_TESTNET_FORKS=OFF -DCMAKE_BUILD_TYPE=Release cmake --build build --target sost-node sost-miner sost-cli -j"$(nproc)"

A different compiler or libc can legitimately produce a different hash. That alone is not evidence of tampering — but an official downloaded binary must match exactly.

Back up, before you touch anything

TS=$(date -u +%Y%m%d-%H%M%S) cp -a ~/sost-keys/your-wallet.json ~/backup/your-wallet.$TS.json # your wallet cp -a build/sost-node build/sost-node.prev.$TS # the binaries you run now cp -a build/sost-miner build/sost-miner.prev.$TS cp -a build/sost-cli build/sost-cli.prev.$TS sudo cp -a /etc/systemd/system/sost-node.service /root/sost-node.service.$TS # if you use systemd

Copy the wallet backup somewhere off this machine as well. The key inside it receives every block you mine.

Step 2 — Inside the window: stop, install, restart

Stop the right process, by name of service or by PID. Never use a blanket pkill -f sost: on a machine that also runs a node, a CLI or another miner, it kills things you did not mean to kill.

A · systemd service (typical for a node on a server)

sudo systemctl stop sost-node sudo install -m 0755 ~/sost-v1622/sost-node /opt/sost/build/sost-node sudo install -m 0755 ~/sost-v1622/sost-cli /opt/sost/build/sost-cli sudo systemctl start sost-node sleep 20 && systemctl status sost-node --no-pager | head -8

Loading the chain takes a few minutes on a large chain file. That is normal; the miner will retry meanwhile.

B · Manual terminal (node or miner started by hand)

# find YOUR process and confirm it is the one you think it is pgrep -a sost-miner # shows the pid and the full command line PID=<the pid you just saw> kill "$PID" # by PID. Not by name, not -9 first. # wait for it to exit, then install and relaunch with the SAME command line install -m 0755 ~/sost-v1622/sost-miner build/sost-miner

C · Windows / WSL

Same as B, inside your Ubuntu window. If the miner runs in its own terminal, press Ctrl+C in that terminal — that stops exactly that miner and nothing else. Then install the new binary and start it again with the same command you always use.

Relaunch — the command line does not change

Use exactly the flags you used before. If your old command carried the RPC password in the open, this is the moment to move it into a file (see below); nothing else changes.

./sost-miner \ --wallet ~/sost-keys/your-wallet.json \ --mining-key-label "your-label" \ --genesis genesis_block.json \ --rpc 127.0.0.1:18232 --rpc-user your-user --rpc-pass-file ~/.sost/rpc.pass \ --blocks 999999 --profile mainnet --realtime --threads 8
--wallet + --mining-key-label select the key that signs your blocks. Do not replace them with --address: your V16 jackpot eligibility and your NODE_BIND both depend on that signed identity.

Step 3 — Verify, in this order

# 1. the binary that is RUNNING, not the file on disk PID=$(systemctl show sost-node -p MainPID --value) # or the pid of your manual process sha256sum "$(readlink -f /proc/$PID/exe)" # must equal the published hash # 2. the chain is advancing and matches the network ./sost-cli --rpc 127.0.0.1:18232 --rpc-user your-user --rpc-pass-file ~/.sost/rpc.pass \ --wallet ~/sost-keys/your-wallet.json getbalance # 3. RPC and P2P are listening ss -ltn | grep -E '18232|19333' # 4. your miner is building templates and getting blocks accepted # look for: [MINING] h=NNNNN ... and -> submitted to node OK

Then check that a block you mine is credited to your usual address — the one your wallet label maps to. It does not change with this upgrade.

Your RPC password

There is no SOST-wide RPC password. Each operator sets one for their own node. Nobody can give you "the SOST RPC password", and nobody should ever ask you for yours — or for your wallet keys.

It is not your wallet passphrase either. The node and the miner (and the CLI) must use the same credentials because the miner authenticates to your node.

mkdir -p ~/.sost && umask 077 openssl rand -base64 30 > ~/.sost/rpc.pass chmod 600 ~/.sost/rpc.pass

Then point everything at the file instead of typing the secret:

sost-node --rpc-user your-user --rpc-pass-file ~/.sost/rpc.pass ... sost-miner --rpc-user your-user --rpc-pass-file ~/.sost/rpc.pass ... sost-cli --rpc-user your-user --rpc-pass-file ~/.sost/rpc.pass ...

The file must be mode 600, owned by you, one line and nothing else — the binaries refuse anything else rather than reading a secret others can see. If your node runs under systemd, the unit names the path, so the password no longer appears in systemctl show or in ps:

ExecStart=/opt/sost/build/sost-node --genesis genesis_block.json --chain chain.json \ --rpc-user ${RPC_USER} --rpc-pass-file /etc/sost/rpc.pass --profile mainnet --p2p-enc on

HTTP 401 — what it means and what to check

From v16.2.x the miner says it plainly: *** RPC AUTHENTICATION REJECTED (HTTP 401) ***. That is not a rejected block — the node never validated it. Check, in order:

  • the same --rpc-user on node and miner;
  • the same password file contents (a trailing edit, a second line, or a copied space are the usual culprits — the file must hold one line);
  • the node actually restarted after you changed its password;
  • you are talking to your node (--rpc 127.0.0.1:18232), not someone else's.

Rotating it without breaking mining

The order matters: if you change one side only, the miner submits blocks the node refuses.

umask 077 openssl rand -base64 30 > ~/.sost/rpc.pass.new # 1. write the new secret cp -a ~/.sost/rpc.pass ~/.sost/rpc.pass.old # 2. keep the old one mv ~/.sost/rpc.pass.new ~/.sost/rpc.pass # 3. one atomic swap sudo systemctl restart sost-node # 4. node first # 5. then restart the miner (it reads the same file) # 6. verify: no "RPC AUTHENTICATION REJECTED" in the miner output

Your wallet: v1 keeps working

A plaintext (v1) wallet works exactly as before — no conversion, no deadline. The miner loads it, warns once that its private keys are readable by anything that can read the file, and mines.

Encrypting it (v2: scrypt + AES-256-GCM) is optional. If you do it, the procedure never overwrites your only copy:

# 1. export an ENCRYPTED COPY (the original stays where it is) sost-cli --wallet ~/sost-keys/your-wallet.json wallet-export \ --encrypted --output ~/sost-keys/your-wallet.v2.json # the passphrase is typed twice, with the terminal NOT echoing it # 2. RECOVERY DRILL — restore the copy into a different file and compare sost-cli --wallet /tmp/restore-test.json newwallet sost-cli --wallet /tmp/restore-test.json wallet-import --encrypted \ --input ~/sost-keys/your-wallet.v2.json diff <(sost-cli --wallet ~/sost-keys/your-wallet.json listaddresses) \ <(sost-cli --wallet /tmp/restore-test.json listaddresses) && echo "SAME ADDRESSES" # 3. only now, mine one block with the encrypted wallet sost-miner --wallet ~/sost-keys/your-wallet.v2.json --mining-key-label "your-label" \ --wallet-passphrase-file ~/.sost/wallet.pass ...rest of your usual flags...
Keep the v1 file until the encrypted one has mined a block. The passphrase cannot be recovered: lose both it and your backup and the SOST controlled by those keys is gone for good. Encryption protects the file at rest — it does not protect a machine somebody else already controls while the miner is running.

Encrypting does not change your address or your SbPoW identity: it is the same keys in a different container. And you never need to move SOST to another address to encrypt a wallet.

After #30,000 — NODE_BIND, heartbeats and the Jackpot

Only if you want to enter the DTD Jackpot V2 draw. Normal DTD needs none of this: no NODE_BIND, no heartbeats, no node key.

A node key is not your wallet key and not your RPC password. It is a separate 32-byte key that identifies your node, authorised on-chain by your mining key.
# 1. create the node key (after #30,000) mkdir -p ~/.sost && umask 077 openssl rand -hex 32 > ~/.sost/node.key chmod 600 ~/.sost/node.key # SAVE A COPY somewhere safe # 2. build the NODE_BIND with the SAME label your miner signs blocks with sost-cli --wallet ~/sost-keys/your-wallet.json \ --mining-key-label "your-label" \ createnodebind 1 --node-key-file ~/.sost/node.key # -> prints the raw transaction hex; broadcast it: sost-cli --rpc 127.0.0.1:18232 --rpc-user your-user --rpc-pass-file ~/.sost/rpc.pass \ sendrawtransaction <the hex> # 3. let the node heartbeat by itself: add to its command line / unit # --node-key-file /etc/sost/node.key then restart the node once # 4. check your eligibility before #30,186 curl -s -u "your-user:$(cat ~/.sost/rpc.pass)" -H 'content-type: application/json' \ --data '{"method":"checkhistoricaljackpoteligibility","params":["sost1your...address"],"id":1}' \ http://127.0.0.1:18232/

--mining-key-label matters: the bind must authorise the key that actually signs your blocks. If you omit it the CLI uses the label default, and if your mining key carries a different label the bind would be useless — the tool now lists the labels in your wallet when it cannot find the one you asked for.

The first V2 jackpot, at #30,186, requires a valid bind and at least 3 SbPoW blocks in the previous 2,016, but zero heartbeats — no epoch has completed yet. The requirement then ramps 1/1 → 2/2 → 3/3 and settles at the permanent 3 of the last 4 epochs from #31,338. Running more nodes never adds weight: node participation is a gate, your PoW is the weight.

Rolling back

Nothing in v16.2.x changes the on-disk chain format, so a rollback is the old binary and nothing else — no reindex, no migration, in either direction. Every previous release stays downloadable with its own hash list.

sudo systemctl stop sost-node sudo install -m 0755 /opt/sost/build/sost-node.prev.<timestamp> /opt/sost/build/sost-node sudo systemctl start sost-node
One caveat. A wallet you encrypted with v16.2.x cannot be read by a pre-v16.2 binary. If you encrypted and then roll back, point the old binary at the v1 file you kept.
